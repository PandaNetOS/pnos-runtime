# pnos-runtime 性能 SLO 设计（企业级）

> 范围：**仅性能指标维度**。安全（鉴权/TLS/审计）、持久化、韧性（supervisor/优雅关停）见 `enterprise-roadmap.md`。
> 基线环境：Windows 11 / 8 核 16GB / release 二进制 / 单节点。所有数字均来自 2026-09-10 本机会话实测（压测脚本 `D:/PNOS/.pnos-data/bench*.py`）。
> 状态划分：✅ 达标 / ⚠️ 部分达标或需补测 / ❌ 不达标 / ❓ 未测（未知）。

---

## 1. 定位与角色

pnos-runtime 是 **控制面 + 轻数据面** 混合服务：
- **控制面**：组件注册/心跳/查询、系统信息、商店、应用管理（`/api/v1/*`，HTTP JSON）。
- **轻数据面**：`/app/:id` 反向代理到后端 Agent（`proxy.rs`）。

企业级评审不看"峰值 QPS 高不高"，而看 **SLI 是否可量化、SLO 是否签了字、长尾与过载是否驯服、退化是否可见**。

## 4. 关键缺口与 remediation

### 4.1 P7 过载无保护（❌ 一票否决项）
现状：全局无任何 HTTP 超时、`DefaultBodyLimit`、并发上限、限流。修复 stats 后单端点好了，但**结构上仍无系统性过载保护**——一个异常慢调用（大文件代理、子进程卡死）仍会拖垮全部。
- Remediation：全局 `Timeout` + `DefaultBodyLimit` + 并发信号量 + 限流中间件（如 `governor`）；过载时返回 429 + `Retry-After`，而非排队雪崩。见 `enterprise-roadmap.md` E3。

### 4.2 P8 零埋点（❌ 不可观测）
现状：runtime 只有主机指标（CPU/内存/磁盘/负载），**零应用级指标**（无 QPS、延迟分位、错误率、队列长度、worker 阻塞率、句柄数、任务心跳）。企业 SRE 无法计算 SLI。
- Remediation：新增 `/api/v1/metrics`（Prometheus 文本格式），最小集：
  1. 每端点：请求计数、错误计数、耗时直方图（算 p50/p95/p99/p99.9）
  2. 进程内：tokio worker 阻塞率、活跃任务数、句柄/FD 数
  3. 业务：组件数、离线数、Agent 崩溃/重启次数、商店刷新耗时
  4. 任务心跳：每个后台任务最后成功 tick 时间（解决"后台循环静默死"）
- 见 `enterprise-roadmap.md` E2。

### 4.3 P3/P6/P9/P10/P11 未测（❓）
见 §5 测试计划。

### 4.4 P5 列表无分页（⚠️）
现状：`/components` 全量返回，2000 条 873KB；1 万条 ≈ 4.4MB/次，前端 5s 轮询 = 近 1MB/s 持续带宽。
- Remediation：分页（`?page=&page_size=` 默认 50）+ 字段过滤（`?fields=`）；响应包 `total` 字段供前端分页。

## 5. 缺失测试计划（把"未知"变"已知"）

| 测试 | 方法 | 预期/达标线 | 关联 SLI |
|---|---|---|---|
| p99.9 延迟 | 各端点并发 50 跑 60s，取 p99.9 | 控制面 p99.9 < 100ms | P3 |
| 24h 内存增长 | 常驻 + 周期心跳/查询，每小时记 RSS | 增长 < 20%（无泄漏/无界增长） | P6 |
| 代理吞吐 | `/app/:id` 代理大文件（1GB）测带宽与内存 | ≥ 500Mbps，内存不随文件增大 | P9 |
| 代理 OOM 防护 | 代理超 `body_limit` 的大响应 | 返回 413/502，runtime 不崩 | P7/P9 |
| 最大并发连接 | 逐步加压至连接数上限 | 明确上限并文档化；超限时 429 而非崩 | P10 |
| 冷启动耗时 | 重启到 `/health` 200 的耗时 | < 2s | P11 |
| 优雅关停耗时 | `docker stop` / SIGTERM 到进程退出 | < 5s，子进程全回收 | P11 |
| 过载实验 | stats+components 拉满时注入大 body 代理 | 控制面仍健康（限流生效） | P7 |

## 6. 容量模型

- **心跳需求** = Agent 数 / 心跳间隔。1000 Agent @15s ≈ 67 QPS；1 万 Agent ≈ 667 QPS。
- **写路径实测** 6000/s → 余量 ~90×（1 万 Agent 场景）。
- **瓶颈不在注册/心跳，在监控端点（已修）与列表接口（需分页）**。
- 代理吞吐需实测（P9）——若 Agent 经 runtime 转发大流量，可能成为真实瓶颈。

## 7. 不可破坏的约束（设计 SLO 时遵守）

| 约束 | 来源 | 含义 |
|---|---|---|
| API envelope `{code,message,data}` | 前端 `api/index.ts` 统一解包 | 改了全站崩 |
| `/system/info`、`/system/stats` 字段被前端硬解析 | pnos-web | 只能加字段不能改名改结构 |
| SDK 注册 `POST /api/v1/components/register`、心跳 15s、超时 30s | pnos-sdk | 契约面不能动 |
| 静态目录 `/var/www/pnos-web` | main.rs:68 ↔ PNOS-docker Dockerfile:12 | 不能改（组装镜像依赖） |
| 前端纯轮询无 WS | pnos-web grep 0 命中 | WS 实时能力不在本期 |

> 注：新增 `/api/v1/metrics` 是**新增端点**，不触碰上述契约；分页为 `/components` 增加可选 query 参数，向后兼容（不传则默认全量/首屏）。

## 9. 验收标准（何时可宣称达标）

全部满足方可宣称"性能指标达到企业级"：
1. P1/P2/P3 通过内部 metrics 持续可见（非仅压测），且达标 ≥ 1 周。
2. P7 过载实验通过：注入异常负载时控制面仍健康，无雪崩。
3. P6 24h 长跑无内存增长、无任务静默死亡。
4. P9 代理吞吐 ≥ 500Mbps 且不 OOM。
5. P5 万级组件分页后 p99 < 100ms。
6. P10/P11 并发上限与重启耗时文档化且达标。
7. 上述全部有 CI 回归（benchmark 固化进流水线，防退化）。
